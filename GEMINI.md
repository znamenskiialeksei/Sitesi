## БЛОК I: АБСОЛЮТНЫЙ ИМПЕРАТИВ И БЕЗОПАСНОСТЬ: ПРАВИЛА ПОВЕДЕНИЯ АГЕНТА

<a name="11-базовое-правило-разработки-zero-terminal--zero-popup-policy"></a>
### 1.1. Базовое правило разработки: Zero-Terminal & Zero-Popup Policy
> **Императивное требование пользователя:**  
> **Все выявленные проблемы устраняются напрямую в кодовой базе без вызова терминальных команд и всплывающих окон подтверждений.**

* **Запрет на вызовы терминала:** Запрещено вызывать команды терминала (`run_command`, PowerShell, CLI, Bash, cmd) для поиска по коду, инспекции, тестирования или применения правок, чтобы исключить появление всплывающих модальных окон подтверждения у пользователя (таких как `Allow finding ...`, `Allow this time`, `Yes, allow`).
* **Прямая работа с файлами:** Любой аудит, поиск, рефакторинг и устранение ошибок выполняются исключительно через прямое чтение и редактирование файлов проекта (`view_file`, `grep_search`, `find_by_name`, `list_dir`, `replace_file_content`, `write_to_file`).
* **Автономность правок:** Кодовая база обновляется детерминированно, чисто и без промежуточных интерактивных блокировок.

<a name="12-принцип-тотального-системного-устранения-первопричин-total-root-cause-elimination"></a>
### 1.2. Принцип тотального системного устранения первопричин: Total Root Cause Elimination
* **Запрет временных заплаток:** При выявлении любой ошибки, сбоя синтаксиса, кодировок, путей или настроек окружения агенту **категорически запрещено** ограничиваться локальной точечной правкой (костылем) в одном изолированном файле.
* **Системный сквозной аудит:** Агент обязан провести исчерпывающий сквозной аудит всей кодовой базы репозитория, найти ВСЕ подобные и смежные места, определить глубинную первопричину и устранить проблему системно, единообразно и синхронно во всех скриптах, проектах и конфигурационных файлах за одну итерацию.

<a name="13-обязательное-предварительное-детальное-планирование-upfront-detailed-planning"></a>
### 1.3. Обязательное предварительное детальное планирование: Upfront Detailed Planning
> **Императивное требование пользователя:**  
> **Очень детальный план реализации должен предлагаться мне после каждого моего обращения и каждой поставленной задачи. Любые правки кода допустимы только после моего подтверждения.**

* **Обязательный артефакт `implementation_plan.md`:** После любого обращения пользователя и формулирования задачи агент обязан в первую очередь сформировать подробнейший, глубокий структурированный план изменений в артефакте `implementation_plan.md` с запросом подтверждения (`request_feedback: true`).
* **Запрет на несанкционированные действия:** До получения прямого согласия от пользователя (Согласен, Подтверждаю, Делай) внесение изменений в исходный код, создание или удаление рабочих файлов строго запрещено.

<a name="14-неизменность-структуры-папок-и-документов-без-согласования"></a>
### 1.4. Неизменность структуры папок и документов без согласования
* **Императив согласования:** Структура папок и документов проекта, утвержденная пользователем, меняется **строго только по предварительному согласованию с ним**.
* **Регламент предложения изменений:** При необходимости создания новых каталогов, файлов или модификации существующей структуры пользователю предварительно предлагается качественный вариант для утверждения с подробным описанием:
  1. Почему именно так с точки зрения логики и правил программирования;
  2. Каковы конкретные практические преимущества и удобство для пользователя.

<a name="15-папка-утвержденных-планов-изменений-строгая-проектная-изоляция"></a>
### 1.5. Папка утвержденных планов изменений: Строгая проектная изоляция
* **Локация папки планов:** `[Имя-Проекта]\ПЛАНЫ\`
* **Строгая проектная изоляция:** Папка планов создается **строго внутри конкретного проекта** [например, `villa-turaman-airbnb-platform\`], к которому они относятся. Запрещено создавать ее в корне рабочей области.
* **Канонический стандарт именования планов:** Каждый утвержденный и реализованный план сохраняется в данную папку под каноническим кратким именем в цифро-текстовом формате: `ДДММГГГГЧЧмм [Краткое название плана на русском до 45 символов].md` [ДеньМесяцГодЧасыМинуты: время строго после даты, например: `210920261500 Сохранение релиза.md`].
* **Правило чистоты экосистемы:** Файлы «Карта проекта», «Живая лента планов» и их шаблоны ликвидированы и больше никогда не создаются. Все утвержденные планы хранятся как автономные документы в папке планов соответствующего проекта.

## БЛОК II: СРЕДА ВЫПОЛНЕНИЯ VS CODE И POWERSHELL СТАНДАРТЫ

<a name="21-исключительная-среда-пользователя-vs-code-exclusive-workspace"></a>
### 2.1. Исключительная среда пользователя: VS Code Exclusive Workspace
> **Императивное требование пользователя (Высший приоритет):**  
> **Я работаю ТОЛЬКО в программе VS CODE и в его терминале. Все команды должны быть адаптированы под это и продублированы штатными вариантами запуска из интерфейса VS CODE, а также продублированы запуском через задачи в VS CODE.**

* **Исключительная среда пользователя:** Пользователь работает **ИСКЛЮЧИТЕЛЬНО в программе Visual Studio Code** под Windows со встроенным терминалом. Категорически запрещено предлагать действия во внешних окнах, сторонних терминалах или утилитах, оторванных от среды VS Code.
* **Адаптация всех команд:** Все команды, пути и аргументы должны быть на 100% валидны для исполнения во встроенном терминале VS Code под Windows (PowerShell/pwsh, кодировка UTF-8, корректное экранирование пробелов в путях, исполнение из текущей рабочей директории).

<a name="22-обязательный-стандарт-тройного-дублирования-запусков-triple-tier-launch-standard"></a>
### 2.2. Обязательный стандарт тройного дублирования запусков: Triple-Tier Launch Standard
При предоставлении пользователю ЛЮБОГО действия, запуска сценария, команды сборки, очистки, синхронизации или тестирования, агент ОБЯЗАН оформлять инструкцию **строго в 3-х обязательных параллельных вариантах**:
1. **Способ 1: Штатный графический интерфейс VS Code (GUI Launch):**
   - Через Command Palette (`Ctrl+Shift+P` ➔ `Tasks: Run Task`);
   - Через главное меню: `Терминал (Terminal)` ➔ `Запустить задачу... (Run Task...)`;
   - Через горячие клавиши: `Ctrl+Shift+B` (Default Build Task) или клавишу `F5` / `Ctrl+F5` (Run & Debug).
2. **Способ 2: Запуск через задачи в VS Code (`.vscode/tasks.json`):**
   - Точное отображаемое имя задачи из `.vscode/tasks.json` (например, `"🚀 0. SPARK: ПОЛНЫЙ ЗАПУСК ВСЕГО"`, `"🧹 10. SPARK: Принудительная очистка портов (порт 3000)"`, `"🧹 Очистить архивные дубли и корень"`).
   - Для ЛЮБОГО действия в проекте ОБЯЗАНА существовать соответствующая преднастроенная задача в файле `.vscode/tasks.json`.
3. **Способ 3: Нативная команда встроенного терминала VS Code (Integrated Terminal):**
   - Готовая строка для копирования в 1 клик во встроенный терминал VS Code (PowerShell / pwsh) без риска синтаксических сбоев.

<a name="23-современный-powershell-7-pwshexe-и-конфигурация-vs-code"></a>
### 2.3. Современный PowerShell 7 pwsh.exe и конфигурация VS Code
* **Переход на PowerShell 7 (`pwsh.exe`):** Пользователь работает в современной среде с установленным PowerShell 7 (`pwsh.exe`). Все задачи в `.vscode/tasks.json` вызываются через команду: `pwsh -ExecutionPolicy Bypass -File ...`. Запрещено принудительно вызывать устаревший Windows PowerShell 5.1 (`powershell.exe`).
* **Конфигурация `.vscode/settings.json`:** В файле настроек рабочего пространства фиксируется нативная привязка:
  - `"[powershell]": { "files.encoding": "utf8bom" }`
  - `"files.autoGuessEncoding": false`
  - `"files.encoding": "utf8"`
  - `"terminal.integrated.defaultProfile.windows": "PowerShell 7"`
  - `"terminal.integrated.profiles.windows": { "PowerShell 7": { "path": "pwsh.exe", "args": ["-NoLogo", "-ExecutionPolicy", "Bypass"] } }`
* **Полный отказ от костылей (Zero Crutches Standard):** В кодовой базе и скриптах категорически запрещены любые временные заплатки: Base64-экранирование кириллицы, байтовые массивы `[byte[]]@(...)`, искусственный перевод служебных сообщений на английский язык. Все сценарии обязаны содержать понятные русские комментарии, чистые русские пути и красивый русскоязычный вывод в консоль.

<a name="24-обязательная-сигнатура-utf-8-bom-для-сценариев-powershell"></a>
### 2.4. Обязательная сигнатура UTF-8 BOM для сценариев PowerShell
* **Физический байт-маркер BOM (`\uFEFF`):** Любой скрипт PowerShell (`.ps1`) в репозитории создается и модифицируется со строгой обязательной сигнатурой BOM (`\uFEFF`, `EF BB BF`).
* **Обоснование:** Сигнатура BOM гарантирует, что синтаксический анализатор как Windows PowerShell 5.1, так и pwsh 7 моментально переключается в полноценный режим UTF-8 до начала парсинга кода. Это на 100% исключает появление кракозябр в строковых литералах и ошибки синтаксиса `ParserError`.

<a name="25-чистое-латинское-именование-файлов-скриптов-ascii-snake_case"></a>
### 2.5. Чистое латинское именование файлов скриптов: ASCII snake_case
* **Исключение кодировочных искажений:** Передача кириллических имен файлов через аргументы командной строки в Windows подвержена разрушению кодовых страниц (OEM 866 vs ANSI 1251 vs UTF-8), порождая фатальные ошибки `Аргумент ... для параметра -File не существует`.
* **Императив:** Все исполняемые PowerShell-скрипты автоматизации именуются **строго на латинице (ASCII)** в формате snake_case (например: `clean_accumulator_and_root.ps1`, `rebuild_portable_launcher.ps1`, `bootstrap_accumulator.ps1`, `push_project_to_github.ps1`).

<a name="26-полная-ликвидация-файлов-bat-и-эксклюзивный-запуск-в-vs-code"></a>
### 2.6. Полная ликвидация файлов .bat и эксклюзивный запуск в VS Code
* **Полная ликвидация .bat:** По прямому требованию пользователя все запускаторы с расширением `.bat` (`deploy_and_run.bat`, `ПЕРЕСОБРАТЬ_ПЕРЕНОС.bat` и др.) полностью ликвидированы из всех проектов и больше не создаются.
* **Чистый стандарт VS Code:** Все действия, запуск серверов разработки, сборка, очистка портов, перевод сайта в режим обслуживания и возобновление работы осуществляются **строго через штатные задачи VS Code (`.vscode/tasks.json`)** либо через нативные сценарии PowerShell (`deploy_and_run.ps1`) во встроенном терминале `pwsh.exe`.

<a name="27-тотальный-стандарт-искоренения-скобок-и-длинного-тире-total-zero-brackets--zero-emdash-policy"></a>
### 2.7. Тотальный стандарт искоренения скобок и длинного тире: Total Zero-Brackets & Zero-Emdash Policy
* **Глубинная первопричина:** Символ длинного тире `—` (U+2014) в кодировке UTF-8 состоит из трех байт: `0xE2 0x80 0x94`. Байт `0x94` в системной русской кодовой странице Windows (Windows-1251) является символом закрывающей типографской кавычки `”`. При разборе строк парсер PowerShell воспринимает байт `0x94` как кавычку и досрочно закрывает строковый литерал прямо посреди текста, разрушая синтаксическое дерево. Круглые скобки `()` вызывают аналогичный сбой токенизатора `MissingEndParenthesisInExpression`.
* **Императивный абсолютный запрет:** В проекте категорически запрещено использовать типографское длинное тире `—` (U+2014) и любые круглые скобки `()` внутри:
  1. Любых строковых литералов, сообщений `Write-Host`, `echo` и логов PowerShell/Bash;
  2. Любых комментариев на русском языке в `.ps1`, `.sh`, `.json`, `.js`, `.md`;
  3. Названий задач в `.vscode/tasks.json` (поле `"label"`);
  4. Названий создаваемых папок, файлов, скриптов, сценариев и артефактов;
  5. Любых текстов и заголовков, генерируемых агентом.
* **Единый канонический разделитель:** Везде вместо скобок и длинного тире используется строго стандартный однобайтовый **ASCII-дефис `-` (код `0x2D`)** или двоеточие `:`. Байт `0x2D` во ВСЕХ кодировках мира означает исключительно знак минус/дефис и физически исключает синтаксическую коллизию.
* **Обязанность агента по авто-санитизации:**
  1. При создании любых названий агент обязан автоматически исключать скобки и длинные тире, заменяя их на стандартный дефис `-`.
  2. Если пользователь сам создал или передал название со скобками или длинным тире, агент ОБЯЗАН АВТОМАТИЧЕСКИ нормализовать его в кодовой базе и скриптах (заменив на стандартный дефис `-`), навсегда исключая сбои парсера.
  3. Исторические системные пути со скобками (например, папка Накопителя) определяются в сценариях строго динамически через прямое сопоставление по маске (`$d.Name -like "*перенос*"` или `$d.Name -like "*накопитель*"`).

<a name="28-изоляция-рабочей-папки-options-cwd-в-vscodetasksjson"></a>
### 2.8. Изоляция рабочей папки options cwd в .vscode/tasks.json
* **Механика сбоя:** При запуске задачи VS Code вызывает команду через аргумент `pwsh.exe -Command <команда>`. При этом системный вызов Windows `CommandLineToArgvW` автоматически сбрасывает внешние кавычки, оставляя путь со скобками незащищенным. В результате PowerShell воспринимает скобки как оператор вызова выражения и пытается выполнить несуществующую функцию, падая с ошибкой: `Термин ... не распознается как имя...`.
* **Канонический стандарт изоляции:** Все задачи, запускающие скрипты из папок со скобками или пробелами, ОБЯЗАНЫ указывать путь к каталогу в опции `"options": { "cwd": "${workspaceFolder}/...папка..." }`, а в поле `"command"` передавать строго чистое относительное имя:
  ```json
  "command": "pwsh -ExecutionPolicy Bypass -File .\\скрипт.ps1",
  "options": {
    "cwd": "${workspaceFolder}/Глобальные настройки проекта (накопитель)"
  }
  ```
  Это гарантирует, что в самой строке команды скобок нет вообще, и синтаксический сбой парсера исключен на 100%.

<a name="29-детерминированные-циклы-foreach-в-сценариях-powershell"></a>
### 2.9. Детерминированные циклы foreach в сценариях PowerShell
* **Запрет многострочных конвейеров Where-Object:** Во всех сценариях `.ps1` категорически запрещено использовать многострочные конвейерные блоки `Where-Object { ... }` с кириллическими условиями и операторами `-or`, так как в среде Windows они могут вызывать сбой токенизатора `UnexpectedToken: "}"`.
* **Императивный стандарт:** Любая фильтрация и обход файлов, папок и коллекций реализуются СТРОГО через прямые детерминированные циклы:
  ```powershell
  foreach ($item in $items) {
      $n = $item.Name
      if ($n -eq "имя1" -or $n -eq "имя2") { ... }
  }
  ```

<a name="210-управление-сетевыми-портами-port-conflict-management"></a>
### 2.10. Управление сетевыми портами: Port Conflict Management
* **Предотвращение конфликтов портов:** Перед запуском dev-сервера Next.js на порту 3000 сценарии запуска обязаны в автоматическом режиме проверять занятость порта.
* **Авто-очистка процесса:** При обнаружении стороннего зависшего процесса на порту 3000 сценарий производит детерминированное завершение процесса (`Stop-Process -Id $procId -Force`), выводя понятное информационное сообщение на русском языке в консоль, после чего сервер Next.js запускается без ошибок.

* **Управление режимом обслуживания:**
  - **Пауза сайта [сценарий `pause_site.ps1` / задача VS Code / pwsh]:** Автоматически генерирует фирменную страницу-заглушку `maintenance.html` [в стилистике выбранного варианта платформы], формирует конфигурацию маршрутизации `vercel.json` с кодом ответа `503 Service Unavailable` и отправляет коммит в origin. Код HTTP 503 указывает поисковым роботам [Яндекс, Google], что сайт временно недоступен по техническим причинам, сохраняя все позиции в поисковой выдаче без исключения страниц из индекса.
  - **Возобновление работы [сценарий `resume_site.ps1` / задача VS Code / pwsh]:** Удаляет заглушку и файл перенаправления, фиксирует коммит и пушит в origin, инициируя автоматическую пересборку Next.js платформы на Vercel.
  - **Полная ликвидация вызовов внешнего bash:** Задачи VS Code вызывают сценарии строго через нативный `pwsh -ExecutionPolicy Bypass -File .\pause_site.ps1` без промежуточных консолей и внешних утилит.

### 6.3. Стандарт четкого разделения ролей документов и бесконфликтного прироста знаний
* **Четкое разделение ответственности документов:**
  1. **`GEMINI.md` - ЕДИНСТВЕННЫЙ ЗАКОНОДАТЕЛЬНЫЙ СВОД:** Правила поведения агента, стандарты кода, среды и формул. Прирост новых правил ведется СТРОГО сюда.
  2. **`AGENTS.md` - ТЕХНИЧЕСКИЙ АДАПТЕР И РЕЕСТР:** Краткий перечень директив со ссылками на GEMINI.md без дублирования текста.
  3. **`AI_AGENT_PROMPTS_AND_RULES.md` - БИБЛИОТЕКА ПРОМПТОВ:** Готовые шаблоны запросов, формул переговоров 30/70 и обращения к API.

* **4-этапный регламент бесконфликтного прироста знаний:**
  - **Шаг 1 (Внесение по адресу):** Новое правило - в `GEMINI.md`; новый объект - в `СВОД_СУТИ...`; новый промпт - в `AI_AGENT_PROMPTS...`.

  - **Шаг 3 (Фиксация в хронологии):** Добавление новой записи в `CHAT_CODE_FIXES_CHRONOLOGY.txt`.
  - **Шаг 4 (Автоматическая пересборка переноса):** Синхронизация обновленных мастер-файлов в Уровень 3 (`Глобальные настройки проекта (запускатор перенос)`).

### 6.4. Обязательная Задача 2: Непрерывное ведение хронологии исправлений
* **Файл:** `CHAT_CODE_FIXES_CHRONOLOGY.txt`

<a name="65-автоматический-сквозной-каскад-накопителя-auto-cascade-ssot-policy"></a>
### 6.5. Автоматический сквозной каскад Накопителя: Auto-Cascade SSOT Policy
* **Императивное требование автоматизации:** Для исключения любого рассинхрона регламентов между Накопителем, корневой рабочей областью и дочерними проектами внедрен автоматический превентивный сквозной каскад обновления данных.
* **Механизмы автоматического каскада:**
  1. **Автозапуск при открытии проекта в VS Code [runOn: folderOpen]:** В `.vscode/tasks.json` корневой рабочей области зарегистрирована задача автозапуска `apply_settings.ps1`, срабатывающая без всплывающих окон в фоновом режиме при каждом открытии каталога пользователем.
  2. **Обязательный Шаг 0.0 во всех жизненных скриптах Накопителя:** Каждый сценарий автоматизации [`create_project_backup.ps1`, `push_project_to_github.ps1`, `sanitize_git_tree.ps1` и др.] первым действием до выполнения основной работы осуществляет поиск корня и запуск `apply_settings.ps1`, гарантируя, что любая операция с кодом или Git стартует со 100% актуальными стандартами.
  3. **Штатная задача VS Code:** В палитре задач VS Code доступна моментальная задача ручного запуска: `🔄 [Глобально] Применить настройки Накопителя ко всем проектам`.
* **Защита от дрифта данных:** Любая новая запись в Накопителе [правило, хронология, регламент] детерминированно каскадируется в корень и все 3 проекта комплекса без ручного вмешательства.
